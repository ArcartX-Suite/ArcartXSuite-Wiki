Abyss 的副本流程由 `scripts.yml` 中的生命周期脚本驱动。每个脚本段是一串动作行，按顺序执行；`wait <秒>` 挂起当前脚本（不阻塞其他脚本），`{player}`/`{killer}` 等占位符在运行时展开。

## 选择器

动作行中 `选择器` 位置支持：

| 选择器 | 指向 |
|---|---|
| `@all` | 副本内全部玩家 |
| `@trigger` | 触发者（交互点触发者/死亡者/NPC 点击者等上下文玩家） |
| `@random` | 随机一名副本内玩家 |
| `@dead` | 当前死亡的玩家 |
| 玩家名 | 指定玩家 |

生命周期通常作用于全队，使用 `@all`。交互和 NPC 点击有明确玩家，使用 `@trigger`。怪组清完、阶段进入、世界建造等事件可能没有触发玩家，此时 `@trigger` 选不到人。`@random` 从本局存活成员中随机选择，`@dead` 选择副本判定为死亡的成员。

## 生命周期放哪些动作

文件位置是 `abysses/<地牢ID>/scripts.yml`。下表是固定段名，其他顶层列表为自定义流程段。

| 脚本段 | 时机 | 适合的内容 |
| --- | --- | --- |
| `world-init` | 副本世界准备阶段 | 铺平台、粘贴区域、设置方块。无需玩家的动作 |
| `init` | 入场准备时 | 初始化实例变量。开局前动作有范围限制，不支持的动作会报告错误 |
| `start` | 本局正式开始 | 面向全员的目标提示和开场效果 |
| `complete` | 判定通关后 | 通关奖励、完成提示 |
| `fail` | 判定失败后 | 失败提示或独立失败处理 |
| `player-death` | 成员被判定副本死亡时 | 对死亡者提示、记录死亡后的操作 |
| `all-death` | 触发全员死亡处理时 | 团灭提示，与全局死亡判定策略配合 |
| `exit` | 玩家退出时 | 对退出者提示，不宜在此重复发通关奖励 |

初始化变量使用 `setvar`，玩家提示和战斗效果优先放 `start`。模板的阶段系统会在本局开始后进入入口阶段，避免 `start` 和阶段 `on-start` 同时生成同一怪组。

## 等待、延时与流程段调用

### 等待当前列表

```yaml
warning:
  - "message @all &e3 秒后出现增援"
  - "wait 3"
  - "spawn_group reinforcements"
```

`wait 3` 暂停当前列表三秒，再执行刷怪。其他事件列表仍可运行。本例要求 `reinforcements` 是已定义的手动怪组。

### 稍后调用，当前列表继续

```yaml
start:
  - "delay 3 run_script warning"
  - "message @all &a你现在可以开始行动"
warning:
  - "message @all &e注意侧门增援"
```

`delay <秒> <动作行>` 安排一个稍后执行的动作，不等待它完成。上例先显示“可以开始行动”，三秒后显示侧门提示。若本局已经结束或所属脚本被取消，延时动作不会继续。

### 调用另一个列表

`run_script warning` 按段名调用。常规运行期的子流程拥有独立执行过程，不能假定子流程中的 `wait` 会使调用方也等候。必须按顺序执行的动作，放在同一个列表内，或用阶段条件决定什么时候进入下一阶段。世界准备阶段对子流程的处理不同，作者应把复杂的战斗分支放到正式运行阶段。

## 条件联动怎样选

| 需求 | 写法 | 未满足时 |
| --- | --- | --- |
| 阶段等待某目标完成 | `complete-when: "group_cleared:guards"` | 阶段继续等待 |
| 机关消耗前核对本局变量 | `if_var coins >= 15` | 当前列表停止 |
| 每个玩家分别判断条件 | 交互的 `conditions` 或 `check @trigger <条件>` | 按对应条件处理 |
| 仅跳过一条有条件动作 | `flow_if var:bonus message @all &6挑战已开启` | 跳过本行，继续后面的动作 |
| 转移控制后结束旧分支 | `flow_jump finish` | 进入目标阶段，旧分支不再执行 |

`flow_if` 的条件使用单个无空格的变量或清怪、清房引用。数值比较用 `if_var` 或阶段的完整比较条件。它们的条件语法不能互换。

## 用两个独立流程段发不同奖励

在 `rewards.yml` 定义 `normal_pack` 与 `bonus_pack` 后，可在 `scripts.yml` 使用下面的调用结构。

```yaml
complete:
  - "run_script reward_normal"
  - "run_script reward_bonus"
reward_normal:
  - "if_var bonus == 0"
  - "grant_reward @all normal_pack"
reward_bonus:
  - "if_var bonus == 1"
  - "grant_reward @all bonus_pack"
```

两段各自判断。未命中的守卫停止该子流程，匹配的一段发放对应奖励。将 `bonus` 在 `init` 初始化为 `0`，并只在玩家选择挑战时设为 `1`。测试时分别走两条路线，核对每位成员只得到一份。

## 动作失败和排查顺序

未知动作或执行异常会停止该列表的后续动作。先看日志中的动作名，再核对动作参数、目标 ID 和所需模块。不要在错误动作后安排必需的清理或通关步骤。

奖励未到账时，依次确认事件有没有触发、变量条件是否通过、选择器有没有玩家、奖励集是否存在，最后检查物品来源和交付结果。草稿试跑可检查前面几项流程，真实发奖要进入测试副本验证。

### 全服共享计数

| 动作 | 用法 |
|---|---|
| `global_add` | `global_add <键> [增量]` 累加（默认 +1），命中阈值自动发事件 |
| `global_set` | `global_set <键> <值>` 直接设定 |
| `global_get` | `global_get <键> <变量>` 把全服计数读进实例变量（配合 `check` 判断） |
| `global_reset` | `global_reset <键>` 归零并清阈值触发记录（一轮全服事件结束用） |

**阈值事件**：模块配置 `config.yml` 的 `global-thresholds` 节声明阈值表：

```yaml
global-thresholds:
  reboot_key_fragments: [50, 100]   # 到达 50 / 100 时各发一次 axs.abyss.global_threshold
```

计数每次变更发 `axs.abyss.global_change`（payload：`key`/`value`/`delta`/`dungeon`/`instance`/`player`）；首次跨越阈值额外发 `axs.abyss.global_threshold`（payload 加 `threshold`），同一阈值只触发一次，`global_reset` 后可重新触发。**事件本体（全服防守战/阵营混战等）由 eventpacket 规则或外部玩法模块订阅实现**——abyss 只出数据源。

### 副本内引导（路标/路径渲染）

调用 `api.util.NavigationTargetService`——HUD 目标行 + 客户端路标 + 路径标记链直达目标，到达发事件并可自动跑脚本段。

| 动作 | 用法 |
|---|---|
| `guide_point` | `guide_point <navId> <x,y,z> [到达半径] <标题...>` 全员登记导航目标（同 navId 覆盖） |
| `guide_clear` | `guide_clear <navId\|all>` 撤下目标 |

```yaml
start:
  - "guide_point pump_room 90,64,-55 3 &e前往泵房"

# 到达回调：scripts.yml 里定义 guide_<navId> 段自动运行
guide_pump_room:
  - "guide_clear pump_room"
  - "message @all &a已抵达泵房"
```

到达同时发 `axs.abyss.guide_arrive` 事件（payload：`nav`）。HUD 顶部常驻显示最新一条目标标题；玩家退出/副本结束自动清理；中途进本的玩家自动补推当前目标。ArcartX 路标桥不可用时动作静默跳过。

## 内联脚本与占位符

- 动作行可用 `aria: <表达式>` / `js: <代码>` 前缀走 Aria/JavaScript 脚本（`js:` 需服务端有 Nashorn/GraalJS，否则跳过并警告）
- 条件字段支持 PAPI 占位符比较：`%axsabyss_dungeon_kills% >= 5`（变量列表见[占位符参考](/docs/guide/placeholders)）。
- `check` 动作可在脚本中途做条件判断，不满足即中止本段后续动作

## 实例变量

`setvar`、`delvar`、`addvar` 读写当前副本实例变量。`setvar coins 0` 初始化，`addvar coins 5` 累加，`delvar coins` 删除。后续文字使用 `{var:coins}` 读取。变量随本局结束，不用来保存账号的永久进度。

内置上下文的 `{player}` 来自当前触发者，`{dungeon}` 是地牢显示名，`{dungeon_id}` 是目录 ID，`{instance_id}` 是本局身份。额外事件变量是否存在取决于触发来源。

**预置变量**（进本/推进流程自动写入，无需 setvar）：

| 变量 | 内容 | 来源 |
|---|---|---|
| `{plan}` / `{plan_name}` | 作战方案 id / 显示名 | 地牢定义了 `plans` 时，进本选定的方案 |
| `{floor}` / `{floor_name}` / `{floors_total}` | 当前层序号 / 层名 / 总层数 | floors 模式推进时写入 |
| `{room}` | 当前房间 id | floors 模式进房时写入 |
| `{player}` / `{killer}` 等 | 触发者/击杀者 | 事件脚本上下文 |
