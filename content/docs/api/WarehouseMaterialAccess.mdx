## 获取接口

```java
import xuanmo.arcartxsuite.api.AxsCapabilities;
import xuanmo.arcartxsuite.api.capability.WarehouseMaterialAccess;

WarehouseMaterialAccess api = AxsCapabilities.get(WarehouseMaterialAccess.class);
if (api == null) {
    // 仓库未加载，向玩家说明或使用背包材料。
    return;
}
api.materialsAsync(player, snapshot -> {
    if (!snapshot.available()) {
        player.sendMessage(snapshot.unavailableReason());
        return;
    }
    long amount = snapshot.entries().stream()
        .mapToLong(WarehouseMaterialAccess.Entry::amount).sum();
    player.sendMessage("仓库可用材料总数：" + amount);
});
```

使用包含本接口的配套 API 与模块。每次业务操作时重新获取接口，未加载时返回 `null`；不要在模块重载后继续使用缓存实例。依赖声明见[快速开始](/docs/api/quick-start)。

## 库存与数量

优先使用 `materialsAsync(player, callback)`。调用及回调位于 Bukkit 主线程，数据库读取在后台，物品解码回到主线程。

快照条目包含仓库槽位、物品身份、首次存入时间、真实 `long amount` 与完整物品样本。`Entry.item()` 返回 Count=1 的副本，总量读取 `amount()`。快照独立于 UI 的分页、分类与图标数量。

不可用、未拥有或未解锁的仓库不会作为可取材料。快照绑定玩家，后续快照会替换旧快照，取料只能使用一次。

## 公开调用顺序

| 方法 | 用途 |
| --- | --- |
| `materialsAsync(Player, Consumer<Snapshot>)` | 异步读取可用个人仓库材料 |
| `prepareMaterials(Player, Snapshot, List<Request>, Target, Consumer<Prepared>)` | 整批扣料与完整凭证在同一事务进入 HELD |
| `authorizeDelivery(Player, String, Consumer<Boolean>)` | 条件转换 HELD → APPLYING，成功回调后才允许改目标库存 |
| `completeDelivery(Player, String, Consumer<Boolean>)` | 记录本轮内存落槽结果，不等于原版跨存档已确认 |
| `cancelPrepared(Player, String)` | 只在未授权的 HELD 阶段尝试条件回仓 |
| `recordUncertain(Player, String, String)` | 交付异常转待核对，保留凭证，不自动补发 |

查询优先使用异步方法。所有接口调用和库存修改应在 Bukkit 主线程进行；异步方法的回调也回到主线程。

### 数据结构

```java
record Request(int slot, int amount) {}
record Target(String adapter, String identity, String persistence, String evidence) {}
record Prepared(boolean success, String operationId, String message) {}
```

| 参数或返回值 | 说明 |
| --- | --- |
| `Snapshot.available()` | 当前玩家是否有可用个人仓库，失败原因见 `unavailableReason()` |
| `Snapshot.entries()` | 可用材料条目；使用 `Entry.slot()` 填写请求槽位，`amount()` 为总库存 |
| `Request.slot` / `amount` | 本批取料的仓库槽位与数量，数量须为正整数 |
| `Target.adapter` / `identity` | 容器适配器标识及目标容器身份 |
| `Target.persistence` / `evidence` | 目标存档方式说明及相关槽位变更详情，用于异常核对 |
| `Prepared.success` | 是否已经准备好本批材料，失败时不得修改容器 |
| `Prepared.operationId` | 本批转移的凭证 ID，传给授权、完成、取消或异常记录方法 |
| `Prepared.message` | 操作结果说明，可用于向玩家提示失败原因 |
| `authorizeDelivery` 回调 | `true` 才能继续交付，`false` 时不得修改目标库存 |
| `completeDelivery` 回调 | 是否记录成功；失败后交付结果不确定，应保留凭证核对 |

目标证据应包含本次涉及的玩家/容器槽位前后完整物品数据。配方、位置和数量由服务端重新校验，不能把客户端展示的数量或图标当成取料凭据。

同一玩家只允许一笔在途转移。每批最多九个槽位请求，总需求最多 576 个；超过限制或服务繁忙时会拒绝操作，调用方应处理失败结果。工作台、三种炉子、切石机、锻造台、酿造台与村民交易的材料填入，以及附魔台的青金石、织布机的染料和制图台的辅材补足和信标支付物品补足，均使用此交付流程。

## 调用方责任

1. 在读取快照后生成完整材料计划和目标快照，先检查退回空间。
2. 托管成功后重新检查玩家、InventoryView 与源/目标未发生变化。
3. 授权成功后再次检查，只应用一次；不能对 APPLYING 或 REVIEW 操作自行补发。
4. 主线程落槽成功后记录结果；异常调用 `recordUncertain`，不能猜测性再次存入或交付。
5. 模块关闭或能力实例变化时取消本地等待任务。服务关闭后，不保证仍会调用异步回调。

## 恢复边界

普通 SQL 批量事务不是 Bukkit 背包、工作台矩阵与熔炉区块的共同存档事务。当前原版适配器遗留的交付阶段记录会在重启/热重载后保守进入 REVIEW，不自动重放。
