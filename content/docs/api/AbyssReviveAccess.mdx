## 获取接口

使用 `AxsCapabilities.get(AbyssReviveAccess.class)`。同时从 [AbyssAdmissionAccess](/docs/api/abyss-integration) 读取 `integrationInfo().features().get("reviveTransactions")`。获取到接口且该值为 `AVAILABLE` 时，才开放救援入口。

## 配置与职责

第三方接入和[战术面板](/docs/abyss/native-gameplay)共用本局救援额度。`external-control-owner` 填写接入插件的标识，调用时将同一标识传入 `owner`。`abyss-native` 由 Abyss 保留。

每个副本的 `config.yml` 可以配置以下额度，默认 `0` 表示关闭外部救援。
范围为 0～1000，每名成员每个 runId 独立计数。工作台的结算表单也提供“每人本局救援额度”。

```yaml
requirements:
  external-control-owner: my_dungeon_plugin
  revive-limit: 2
```

接入插件负责判断救援距离和救援者资格，并处理读条与受伤打断。读条完成后调用 `commit`，Abyss 会核对目标是否仍可救援、扣减额度并执行复活。
服主应协调 `player-death` 自动复活脚本和团灭设置，避免读条结束前触发自动复活或判负。结算动作 `revive-players` 和管理员脚本复活有各自的规则，救援额度只用于此处的救援操作。

## 方法声明

```java
public interface AbyssReviveAccess {
    CompletionStage<Status> reviveStatus(UUID runId, UUID playerId);
    CompletionStage<Receipt> reserve(String owner, UUID operationId, UUID runId, UUID playerId,
        String reason, long expectedRevision);
    CompletionStage<Receipt> commit(String owner, UUID operationId);
    CompletionStage<Receipt> release(String owner, UUID operationId);
    CompletionStage<Receipt> query(String owner, UUID operationId);
}
```

## 参数与返回值

所有方法在服务器主线程调用，返回 `CompletionStage`。完成回调可能位于数据库线程，
再次调用 API 或更新玩家 UI 前切回宿主主线程调度器。

在主线程取得状态后，将 `revision` 保存在救援上下文中。开始读条时调用预留方法，保存 `operationId` 供断线后查询。

```java
AbyssReviveAccess api = AxsCapabilities.get(AbyssReviveAccess.class);
if (api == null) return;
String owner = "my_dungeon_plugin";
UUID operationId = UUID.randomUUID();
api.reserve(owner, operationId, runId, targetId, "teammate-rescue", revision)
    .whenComplete((receipt, error) -> {
        // 此回调可能在数据库线程，先保存回执，再切回主线程更新读条 UI。
        // 只有 RESERVED 才开始读条，UNKNOWN 保持待核账。
    });
```

读条结束后在主线程调用 `api.commit(owner, operationId)`。中断时调用 `api.release(owner, operationId)`。响应丢失时调用 `api.query(owner, operationId)`。这些调用均使用预留时的 `owner` 和 `operationId`。

| 方法 | 用途 |
| --- | --- |
| `reviveStatus(runId, playerId)` | 读取 maximum、used、remaining、revision、member、state 和 code |
| `reserve(owner, operationId, runId, playerId, reason, expectedRevision)` | 按状态修订预留一份额度，占用目标 30 秒 |
| `commit(owner, operationId)` | 持久化提交意图，检查原死亡代次，执行真实复活并保存结果 |
| `release(owner, operationId)` | 释放尚未开始提交的预留 |
| `query(owner, operationId)` | 查询原操作，处理预留到期和重启中断状态 |

`operationId` 在同一 owner 下全局唯一。重试必须复用原编号、runId、playerId、reason 和 expectedRevision。
改参数复用编号返回 `OPERATION_CONFLICT`。第一次调用未受理且返回 `STALE_REVISION` 时，
重新读取状态并用新的编号提出新的操作。

## 调用注意事项

| 状态 | 调用方行为 |
| --- | --- |
| `RESERVED` | 开始或继续救援读条 |
| `COMMITTING` | 提交执行中，保持原操作编号查询 |
| `COMMITTED` | 该次复活已确认，额度只扣一次 |
| `RELEASED` | 已释放，未扣次数 |
| `EXHAUSTED` | 没有可预留额度 |
| `REJECTED` | 根据 code 提示，不显示复活成功 |
| `UNKNOWN` | 需要核账，保留占用，不发起替代操作 |
| `NOT_FOUND` | 查无该 owner 下的操作 |

成员离场、死亡代次变化、局已结束或预留过期时，尚未开始执行的提交会释放额度。
传送失败时保持死亡状态且不扣额度。提交执行过程中发生异常，或重启后发现
未完成的 COMMITTING 记录，会保留待核账状态，不自动重做一次复活。
接口超时或异常完成不能解释为失败，也不能重新生成编号重试。

记录随实例世界销毁继续保留，在管理员显式清理模块数据库前可查询。
当前额度修订与本局账本修订一致，其他账本写入也可能使 expectedRevision 过期。
