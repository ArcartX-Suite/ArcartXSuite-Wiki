> **付费模块**

## 概述

EventPacket 模块除了核心的规则触发与动作链系统外，还内置三个独立的后台服务，通过定时任务实现自动化运维能力：

| 服务 | 类 | 功能 | 启动条件 |
|---|---|---|---|
| 实体清理 | `EntityCleanupService` | 定时清理掉落物、怪物等实体（ClearLag） | `entity-cleanup.enabled: true` |
| 定时命令 | `ScheduledCommandService` | 定时执行控制台或玩家命令 | 存在 `enabled: true` 的定时任务 |
| PAPI 监听 | `PapiWatcherService` | 轮询 PAPI 占位符变化、击杀计数和脚本触发器 | 存在对应类型的规则 |

三个服务在 `EventPacketModule.startService()` 中按顺序初始化，在 `stopService()` 中按相反顺序关闭，确保资源正确释放。

## 实体清理服务

`EntityCleanupService` 提供 ClearLag 功能，定时清理服务器中的掉落物、怪物、动物等实体，支持警告倒计时和白名单过滤。

### 工作原理

```
模块启动
  │
  ├─ 读取 entity-cleanup 配置
  ├─ enabled=false 或 interval <= 0 → 不启动
  ├─ 计算清理间隔 (intervalTicks = intervalSeconds * 20)
  ├─ 注册定时清理任务 (AxsScheduler.runTaskTimer)
  ├─ 注册警告任务 (提前 warningSeconds 秒广播)
  │
  └─ 每次清理:
       ├─ 遍历指定世界 (worlds 为空则全部世界)
       ├─ 遍历世界内所有实体
       ├─ shouldRemove 判定:
       │    ├─ 跳过玩家
       │    ├─ 跳过有自定义名称的实体 (skip-named)
       │    ├─ 跳过白名单内实体 (entity-whitelist)
       │    ├─ clear-dropped-items → 清理掉落物 (Item)
       │    ├─ clear-monsters → 清理怪物 (Monster)
       │    ├─ clear-animals → 清理动物 (Animals)
       │    └─ clear-entity-types → 清理指定类型
       ├─ 移除实体 (entity.remove)
       └─ 广播清理消息 (含 {count} 变量)
```

### 配置字段

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `entity-cleanup.enabled` | boolean | `false` | 是否启用实体清理 |
| `entity-cleanup.interval-seconds` | int | `300` | 清理间隔（秒） |
| `entity-cleanup.warning-seconds` | int | `30` | 清理前警告倒计时（秒），0 = 不警告 |
| `entity-cleanup.warning-message` | String | `&c[清理] 将在 {seconds} 秒后清理掉落物！` | 警告消息，支持 `{seconds}` 变量和 `&` 颜色码 |
| `entity-cleanup.cleanup-message` | String | `&a[清理] 已清除 {count} 个实体。` | 清理完成消息，支持 `{count}` 变量 |
| `entity-cleanup.clear-dropped-items` | boolean | `true` | 是否清理掉落物 |
| `entity-cleanup.clear-monsters` | boolean | `false` | 是否清理怪物（`Monster` 接口） |
| `entity-cleanup.clear-animals` | boolean | `false` | 是否清理动物（`Animals` 接口） |
| `entity-cleanup.skip-named` | boolean | `true` | 是否跳过有自定义名称的实体 |
| `entity-cleanup.clear-entity-types` | list | `[]` | 额外要清理的实体类型（`EntityType` 枚举名） |
| `entity-cleanup.entity-whitelist` | list | `[VILLAGER, ARMOR_STAND]` | 不清理的实体类型白名单 |
| `entity-cleanup.worlds` | list | `[]` | 限定生效世界，空 = 所有世界 |

### 清理优先级

`shouldRemove()` 方法按以下顺序判定实体是否应被清理：

| 判定顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 实体类型为 `PLAYER` | 不清理 |
| 2 | `skip-named: true` 且实体有自定义名称 | 不清理 |
| 3 | 实体类型在 `entity-whitelist` 中 | 不清理 |
| 4 | `clear-dropped-items: true` 且实体为 `Item` | 清理 |
| 5 | `clear-monsters: true` 且实体为 `Monster` | 清理 |
| 6 | `clear-animals: true` 且实体为 `Animals` | 清理 |
| 7 | 实体类型在 `clear-entity-types` 中 | 清理 |
| 8 | 以上均不匹配 | 不清理 |

### 警告机制

当 `warning-seconds > 0` 且 `warning-seconds < interval-seconds` 时，注册独立的警告任务。警告任务在清理任务前 `warning-seconds` 秒触发，广播警告消息。

```
清理周期: |<------- interval-seconds -------->|
警告时机:              ^--- warning-seconds ---^
清理时机:                                      ^--- 清理执行
```

### 手动清理

通过管理命令可立即执行一次实体清理，不受 `enabled` 配置限制：

```bash
/axs eventpacket clearlag
```

> 手动清理返回被清除的实体数量。详见 [命令与占位符](/docs/eventpacket/commands#clearlag-子命令)。

### 配置示例

```yaml
entity-cleanup:
  enabled: true
  interval-seconds: 600
  warning-seconds: 60
  warning-message: '&e[清理] 将在 {seconds} 秒后清理地面掉落物！'
  cleanup-message: '&a[清理] 已清除 {count} 个实体。'
  clear-dropped-items: true
  clear-monsters: false
  clear-animals: false
  skip-named: true
  clear-entity-types:
    - ARROW
    - EXPERIENCE_ORB
  entity-whitelist:
    - VILLAGER
    - ARMOR_STAND
    - ITEM_FRAME
  worlds:
    - world
    - world_nether
```

## 定时命令服务

`ScheduledCommandService` 提供定时执行命令的能力，支持两种调度模式：日历触发（1.6.0+）和固定间隔（向后兼容）。

### 调度模式

| 模式 | 配置方式 | 说明 |
|---|---|---|
| 日历触发 | `schedule` 节 | 通过 `SchedulerAPI.scheduleCalendar` 注册，支持 hourly/daily/weekly/interval |
| 固定间隔 | `interval-seconds` + `delay-seconds` | 通过 `SchedulerAPI.scheduleAtFixedRate` 或 `AxsScheduler.runTaskTimer` 注册 |

> 当任务配置了 `schedule` 节且 `SchedulerAPI` 可用时，优先使用日历触发模式；否则降级到固定间隔模式。

### 日历触发模式

`schedule` 节支持四种调度模式：

| 模式 | 配置值 | 触发时机 | 必填参数 |
|---|---|---|---|
| 每小时整点 | `hourly` | 每小时整点触发 | — |
| 每天指定时刻 | `daily` | 每天指定时刻触发 | `time`（`HH:mm` 格式） |
| 每周指定时刻 | `weekly` | 每周指定星期和时刻触发 | `day`（星期名）、`time` |
| 固定间隔 | `interval` | 按固定间隔触发 | `interval-ticks` / `interval-seconds` / `interval-minutes`（按优先级读取） |

```yaml
scheduled-commands:
  # 每天凌晨 3 点执行自动保存
  daily-save:
    enabled: true
    as-console: true
    commands:
      - 'save-all'
    schedule:
      mode: daily
      time: "03:00"

  # 每周一凌晨 4 点重置周常
  weekly-reset:
    enabled: true
    as-console: true
    commands:
      - 'say 周常任务已重置！'
    schedule:
      mode: weekly
      day: monday
      time: "04:00"

  # 每 30 分钟执行一次在线奖励检查
  interval-reward:
    enabled: true
    as-console: true
    commands:
      - 'onlinerewards check-all'
    schedule:
      mode: interval
      interval-minutes: 30
```

### 固定间隔模式

向后兼容模式，通过 `interval-seconds` 和 `delay-seconds` 配置：

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `interval-seconds` | int | `300` | 触发间隔（秒），0 或负数不启动 |
| `delay-seconds` | int | `0` | 首次执行延迟（秒） |

```yaml
scheduled-commands:
  example-save:
    enabled: true
    interval-seconds: 600
    delay-seconds: 600
    as-console: true
    commands:
      - 'save-all'
    broadcast-message: ''
```

### 命令执行

| 执行模式 | 配置 | 说明 |
|---|---|---|
| 控制台执行 | `as-console: true` | 以 `Bukkit.getConsoleSender()` 身份执行 |
| 玩家执行 | `as-console: false` | 对每个在线玩家执行 `player.performCommand` |

#### 控制台模式

控制台模式下，若命令包含 `{player}` 占位符，则对每个在线玩家执行一次（替换为玩家名）；否则执行一次。

```yaml
scheduled-commands:
  # 对每个在线玩家执行一次
  heal-all:
    enabled: true
    as-console: true
    interval-seconds: 60
    commands:
      - 'heal {player}'
```

#### 玩家模式

玩家模式下，对每个在线玩家执行命令。可通过 `permission` 字段过滤目标玩家。

```yaml
scheduled-commands:
  # 仅对有 VIP 权限的玩家执行
  vip-daily-bonus:
    enabled: true
    as-console: false
    permission: "vip.daily"
    interval-seconds: 86400
    delay-seconds: 0
    commands:
      - 'kit vip_daily {player}'
    broadcast-message: '&aVIP 每日礼包已发放！'
```

> 玩家模式下 `{player}` 占位符替换为玩家名。控制台模式下 `{player}` 占位符替换时使用 `CommandSanitizer.validatePlayerName` 清理玩家名，防止命令注入。

### 广播消息

任务执行完毕后，若 `broadcast-message` 非空，则通过 `Bukkit.broadcastMessage` 广播消息，支持 `&` 颜色码。

### 任务字段表

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `enabled` | boolean | `true` | 是否启用该任务 |
| `interval-seconds` | int | `300` | 固定间隔触发间隔（秒），旧模式 |
| `delay-seconds` | int | `0` | 首次执行延迟（秒），旧模式 |
| `as-console` | boolean | `true` | 是否以控制台身份执行 |
| `permission` | String | （空） | 玩家执行模式下的权限过滤，空 = 所有在线玩家 |
| `commands` | list | `[]` | 要执行的命令列表，支持 `{player}` 变量 |
| `broadcast-message` | String | （空） | 任务执行后广播的消息 |
| `schedule` | section | （空） | 日历触发配置，存在时优先于固定间隔模式 |

> `scheduled-commands` 为动态节（`SyncPolicy.dynamicSection`），键名即任务 ID，可定义多个定时任务。`schedule` 节解析失败时降级到旧模式（固定间隔）。

## PAPI 监听服务

`PapiWatcherService` 是 EventPacket 模块的后台轮询引擎，负责三类触发器的检测：PAPI 占位符变化、击杀计数累计和脚本表达式评估。

### 启动条件

模块启动时根据规则配置按需启动 `PapiWatcherService`：

| 条件 | 说明 |
|---|---|
| PAPI 触发器规则 + PlaceholderAPI 已安装 | 轮询占位符值变化 |
| 击杀计数规则（`mob-kill-count`） | 处理实体死亡事件中的击杀记录 |
| 脚本触发器规则（`script-js` / `script-aria`） | 轮询评估脚本表达式 |

> 三类条件满足任一即启动服务。未安装 PlaceholderAPI 但有 PAPI 触发器规则时，输出警告但服务仍会启动（PAPI 部分不生效，击杀计数和脚本部分正常工作）。

### 轮询机制

服务通过 `AxsScheduler.runTaskTimer` 注册定时任务，间隔由 `settings.refresh-interval-ticks` 配置（默认 20 tick = 1 秒）。每次轮询（`tick()`）执行以下操作：

```
tick() 轮询周期
  │
  ├─ 1. PAPI 占位符检测
  │    ├─ 遍历所有 PAPI 触发器规则
  │    ├─ 检查 PlaceholderAPI 是否可用
  │    ├─ 清理离线玩家的缓存状态
  │    ├─ 遍历在线玩家:
  │    │    ├─ 读取占位符当前值
  │    │    ├─ 与上次缓存值对比
  │    │    ├─ 解析为 BigDecimal 数值
  │    │    ├─ 按触发器类型判定 (increase/decrease/threshold)
  │    │    └─ 满足条件 → 分发规则
  │    └─ 更新缓存值
  │
  └─ 2. 脚本触发器评估 (tickScriptTriggers)
       ├─ 遍历所有脚本触发器规则
       ├─ 清理离线玩家的缓存状态
       ├─ 遍历在线玩家:
       │    ├─ 评估脚本表达式 (ScriptConditionEvaluator)
       │    ├─ 与上次状态对比 (false → true 上升沿)
       │    └─ 上升沿 → 分发规则
       └─ 更新状态缓存
```

### 击杀计数处理

击杀计数不通过轮询检测，而是由 `PlayerEventPacketListener.onEntityDeath()` 在实体死亡时主动调用 `recordMobKill()` 方法。该方法在 `PapiWatcherService` 中实现，与轮询逻辑共享同一服务实例。

```
实体死亡事件
  │
  ├─ 获取击杀者 (entity.getKiller())
  ├─ 解析实体元数据
  ├─ 遍历 mob-kill-count 规则:
  │    ├─ 世界/实体类型/MM ID 过滤
  │    ├─ 读取当前击杀数 (内存缓存 → 数据库回退)
  │    ├─ 击杀数 +1
  │    ├─ 持久化到数据库 (eventpacket_kill_progress)
  │    ├─ 判断是否达到 requiredCount
  │    ├─ 达到 → 分发规则
  │    └─ repeatable → 重置计数为 0
  └─ 非 repeatable → 计数保留（不再触发）
```

> 击杀进度优先从内存缓存（`mobKillCounts`）读取，缓存不存在时从数据库回退加载。持久化使用 `repository.setKillCount()` 写入 `eventpacket_kill_progress` 表。

### 状态缓存管理

`PapiWatcherService` 维护三个缓存表，在玩家退出时通过 `clearPlayer()` 清理：

| 缓存 | 类型 | 说明 |
|---|---|---|
| `lastValues` | `Map<String, Map<UUID, String>>` | 每个规则每个玩家的上次占位符值 |
| `mobKillCounts` | `ConcurrentHashMap<String, Integer>` | 击杀计数缓存（key: `uuid\|ruleId`） |
| `scriptLastState` | `ConcurrentMap<String, Map<UUID, Boolean>>` | 每个规则每个玩家的上次脚本状态 |

> 每次轮询时自动清理离线玩家的缓存（`state.keySet().removeIf(uuid -> !onlinePlayerIds.contains(uuid))`），避免内存泄漏。玩家退出时 `PlayerEventPacketListener` 调用 `watcherService.clearPlayer()` 主动清理。

### 数值解析

PAPI 触发器要求占位符值能解析为数字。`parseNumericValue()` 方法处理流程：

1. 去除空白和逗号分隔符（如 `1,234` → `1234`）
2. 使用正则 `[-+]?\d+(?:\.\d+)?` 匹配
3. 解析为 `BigDecimal`
4. 解析失败返回 `null`，规则跳过

> debug 模式下数值解析失败会输出 `INFO` 级别日志，包含规则 ID、旧值和新值。

### 脚本评估细节

脚本触发器通过 `ScriptConditionEvaluator.passes()` 评估表达式，仅在从 `false` 变为 `true` 的**上升沿**触发：

| 上次状态 | 当前状态 | 是否触发 |
|---|---|---|
| `false` | `true` | 是（上升沿） |
| `true` | `true` | 否（持续 true） |
| `true` | `false` | 否（下降沿） |
| `false` | `false` | 否（持续 false） |

> 脚本评估异常时跳过该玩家本轮评估，debug 模式下输出 `FINE` 级别日志。脚本触发器详见 [触发器详解](/docs/eventpacket/triggers#脚本触发器) 和 [条件系统](/docs/guide/conditions)。

## 服务生命周期

三个服务在模块启停时按固定顺序管理：

### 启动顺序

```
EventPacketModule.startService()
  │
  ├─ 1. JdbcEventPacketRepository 初始化 (建表)
  ├─ 2. EventPacketDispatchService 创建
  ├─ 3. PapiWatcherService 创建并启动 (按需)
  ├─ 4. PlayerEventPacketListener 注册
  ├─ 5. EntityCleanupService 创建并启动
  ├─ 6. ScheduledCommandService 创建并启动
  └─ 7. ChemdahEventBridge 注册 (按需)
```

### 关闭顺序

```
EventPacketModule.stopService()
  │
  ├─ 1. ChemdahEventBridge 注销
  ├─ 2. ScheduledCommandService 关闭
  ├─ 3. EntityCleanupService 关闭
  ├─ 4. PlayerEventPacketListener 注销
  ├─ 5. PapiWatcherService 关闭
  ├─ 6. EventPacketDispatchService 关闭 (清理缓存)
  └─ 7. Repository 关闭 (释放连接池)
```

> `EventPacketDispatchService.shutdown()` 清理 `firedRulesCache` 和 `cooldowns` 缓存。`PapiWatcherService.shutdown()` 取消定时任务并清理所有状态缓存。`EntityCleanupService.shutdown()` 取消清理任务和警告任务。
